CHAPTER 01 / 28 · CODING AGENT ENGINEERING

AI Coding Agent 的演进：从建议到行动

为什么代码生成模型还不等于会写软件的 Agent？从一次性补全、对话编辑到工具驱动的闭环，建立解释整门课程的核心模型。

从一个失败场景开始

假设开发者提出：“修复一个 Python 测试失败的问题。”代码补全工具可以根据局部上下文生成一段补丁，但它不知道补丁能否通过测试。一个具备工具能力的 Coding Agent 则可能先读取失败堆栈、定位测试、修改代码、重新运行测试，再依据反馈继续行动。

两者都使用语言模型，但模型建议与可观察的执行闭环不是同一回事。理解差别，比背诵任何产品内部模块名称更重要。

能力是怎样一步步增加的

面向开发者的 AI 工具大致经历了三个并行演进方向，而不是严格替代的三代产品。

交互形态模型获取的上下文主要长处典型缺口
编辑器内补全光标附近、已打开文件低摩擦快速续写难以验证运行结果
对话式代码助手用户贴入问题、文件片段解释与方案迭代工具结果往往由人搬运
工具驱动 Coding Agent任务、工具定义、历史结果与策略把读、改、测连接成闭环增加执行风险、成本与状态复杂度

这些形态至今可以共同存在。智能补全不一定需要复杂 Agent；受监管的代码变更也未必应该允许自动执行。

把 Agent 精确定义为一个控制系统

为了避免把所有使用 LLM 的程序都称为 Agent，本教程采用一个工程性定义：系统能基于目标选择行动，通过工具或环境获得观察，再根据观察决定下一步，并受明确停止条件约束。这是一种用于教学的定义，并非所有研究文献的统一标准。

最简单的控制循环可表达为：

state = initialize(user_goal)
for step in range(max_steps):
    proposal = model(state, available_tools)
    if proposal.is_final_answer:
        return proposal.answer
    approved = policy_check(proposal)
    observation = execute_or_reject(approved)
    state = append_observation(state, proposal, observation)
return "stopped: step budget exhausted"

这个伪代码暴露四个不能省略的问题：哪些行动被允许、执行失败如何反馈、如何记录状态、何时结束。模型的权重并不能自动解决这些工程问题。

Harness：将模型变成可靠工作流的外壳

Harness 可以理解为围绕模型构建的执行编排层，负责消息、工具、权限、状态、记录与停止条件。它不等于某个固定层数的内部架构，不等于 Agent SDK，也不是对 Claude Code 私有源码的独家命名。

在生产系统中，还会出现沙箱、工作区隔离、人工确认、输出截断、成本统计与评估。不同实现会组合这些能力，但不能因为有循环就默认安全或可靠。

逐步追踪一次“修复测试”的行动

  1. 理解：用户提交失败描述与仓库路径，系统整理允许访问的范围。
  2. 读取：模型选择读取测试与实现文件；Harness 检查路径是否在授权工作区。
  3. 修改：模型提出补丁；执行层验证目标文件与变更影响，必要时请求人工确认。
  4. 检验：测试工具返回退出码、日志与失败摘要；模型以结果为证据继续修正。
  5. 退出：测试通过、用户停止、预算耗尽或无法恢复的错误，都应有明确终止分支。

重要限制

“工具返回退出码 0”不等于业务需求已经满足；测试通过也不意味着无安全漏洞。Agent 的完成判断需要外部验收标准。

哪些主张能作为事实，哪些只能是设计假设

关于 Claude Code，我们可以引用官方文档对命令行、工具扩展、Skills、Hooks、Subagents 的说明，或复现公开 API 的请求与响应。没有证据时，无法可靠地断言“内部共有七个组件”“上下文总在某固定百分比压缩”或“模型调用模块只有若干行”。

因此本教程使用三个标签：官方公开契约（有文档定义）、可观察行为（可复现实验）、教学设计（我们自己选择的结构与实现）。后面的所有设计图都遵循这一区分。

动手辨认真正的反馈循环

练习：任选“自动补全函数”“根据错误日志生成补丁”“运行测试后自动修复”三个场景，写出它们的状态、动作、观察和停止条件。如果缺少环境观察，请解释为什么它仍是辅助生成而非完整的可验证闭环。

掌握这个区分后，就能进入第 02 章建立证据优先的研究环境，再到第 03 章亲自实现最小循环。
