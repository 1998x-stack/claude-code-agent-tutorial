CHAPTER 16 / 28 · CODING AGENT ENGINEERING

实现可审计的权限网关：逐请求审批与拒绝优先

用三态决策、完整工具参数指纹和单次人工审批，解释实际执行前必须独立完成的权限检查；示例不运行任何高权限工具。

把审批从提示词移到宿主执行器

假设模型提出“将 docs/intro.md 覆写为新文本”。这可能正是用户要的操作，也可能来自一次错误的文件路径推断。模型输出 approved=true 并不能证明用户看过这一次写入请求。正确的 Harness 必须明确区分工具意图、静态策略、用户的逐次确认、真正的副作用。

第 15 章讨论公开权限机制，本章仅构造一个可以离线验证的最小审批网关，并刻意不执行任何文件修改。

权限决策要有三态，而不是一个布尔值

allow 表示当前规则已经允许执行；deny 表示当前规则拒绝执行；ask 表示需要更明确、可验证的人工判断。将三态压成一个布尔值，会丢失“需要询问但尚未同意”的重要中间态。

我们的模拟器使用第 15 章的 Policy，其中 deny 优先、ask 次之，且受教学模式约束。它不解析真正的 Bash 通配规则，也不模仿 Claude Code 的完整 Hook 和受管理策略。

一次批准究竟应该绑定什么

当 UI 展示“将某路径改成某内容”时，审批必须和完整工具名与参数绑定；不能仅绑定工具名，否则先批准 Edit("docs/a.md")，随后可能被误用到 Edit("secrets.env")。

req = ToolRequest("Edit", {
    "path": "docs/a.md", "content": "hello"
})
digest = req.fingerprint()
gate = PermissionGateway(Policy(ask=frozenset({"Edit"})))
print(gate.evaluate(req))  # ("ask", ...)
human = Approval(digest, approved_by="user", decision="approve")
print(gate.evaluate(req, human))  # ("allow", ...)
print(gate.evaluate(req, human))  # ("deny", ... replay)

示例使用稳定 JSON 生成 SHA-256 摘要，并且将同一审批视为一次性。这里的摘要不证明审批来自真正的用户：生产中仍需可信 UI、会话身份、随机不可猜测审批 ID、有效期与原子消费记录。

失败路径与可审计 Tool Result

未知工具直接拒绝；参数变化后的旧批准拒绝；策略存在 deny 时，即便提交了有人签名的批准也拒绝。执行失败应该与授权成功分开记录：allow 并不意味着文件已经写入成功，而仅是进入受控执行器的前提。

判定应执行的动作回传给模型
allow调用真正执行器，再收集结果真实返回值 / 错误
ask停止并等待用户确认当前尚无执行结果
deny不执行拒绝原因 / 可恢复建议

不能把模型自己生成的工具参数放进 Approval 结构就算完成审批；该结构必须由可信宿主单独产生。

官方 Claude Code 权限的额外层次

Claude Code 官方权限文档包含工具名和参数匹配规则、工作目录、受管理设置和 Hook。真实规则优先级仍要考虑审批模式、受保护路径、子代理、MCP 与沙箱。尤其“允许执行某个 Bash 命令”并不等于“该命令访问文件和网络都受限制”，后一项由运行时 OS 沙箱承担。

不要把教学摘要当作安全证明

此示例用可复现的 SHA-256 对比确保本地请求参数一致，但它没有认证、授权撤销、并发幂等或真正的安全存储。生产使用必须补上服务端凭据、会话边界与并发保护。

可运行验证：拒绝、变化与重放

源码见 examples/permission_gateway.py。运行 python3 -m unittest discover -s examples -p 'test_*.py'。测试明确覆盖请求需要批准、拒绝优先、旧批准不能匹配新参数、一次性消费、模型自报批准无效与未知工具拒绝。

练习：添加由 UI 提交的 approval_id，确保两个拥有相同参数但不同实际执行意图的请求不会错误共享授权；随后用并发测试确认相同 ID 不能被双重消费。
