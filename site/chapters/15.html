CHAPTER 15 / 28 · CODING AGENT ENGINEERING

Claude Code 权限系统：规则优先级、模式与安全边界

依据最新公开文档核验 deny/ask/allow、Agent SDK 权限链和常用模式，使用可测 Fail-Closed 策略理解权限，不将简化规则器冒充内部源码。

为什么权限不能写在 Prompt 里就算完成

一个 Coding Agent 即使被告知“不要修改生产配置”，仍有可能从不可信文件中读到相反指令，或提出看似无害却带有副作用的工具调用。真正的访问控制必须在执行器外部、基于实际工具名称和参数进行，而不是依赖模型对风险的自我判断。

Claude Code 文档明确区分 allow、ask、deny 规则及模式；调用行为由产品权限系统执行，提示词与 CLAUDE.md 主要约束模型尝试做什么，却无法替代规则。

规则链：拒绝先于询问，询问先于允许

官方规则采用 Tool 或 Tool(specifier) 形式。例如 deny 中的 Bash(git push *) 能阻止匹配调用，即便另一条 allow 包含 Bash(git *)。此处通配符的精确解释应查官方文档，不能自造一个不等价的正则规则器。

规则对调用的作用不仅是是否弹框：裸工具名称被拒绝时可能使工具从模型可用上下文中隐藏；按路径或命令指定则通常只匹配具体调用。

模式是用户交互策略，不是信任等级的简单七段梯

当前官方文档列出 default（Manual）、acceptEdits、plan、auto、dontAsk、bypassPermissions 等模式。可用性与行为受环境、版本及托管策略影响。尤其 auto 在可用时包含后台分类器，而 bypassPermissions 跳过许多常规确认，但并不等于所有操作都能自动通过。

模式主要意图安全注意
default / Manual对常见编辑、Shell 等动作请求确认默认仍应最小授权
plan偏向探索与规划，不做常规写入行为与 auto 的可用性有关
acceptEdits允许特定范围的文件操作不应扩展到任意副作用
auto自动评估并执行例行动作分类器与配置边界必须核对
dontAsk对本应询问的请求采取拒绝已显式允许的工具仍可运行
bypassPermissions在隔离环境减少权限提示只能谨慎用于安全隔离环境

不能把模式理解成“AI 证明自己可信就按等级自动升级”，也不能保留旧稿“固定七种模式”的无版本断言。

Agent SDK 的权限流程包含额外步骤

官方 Agent SDK 权限文档描述 Hook、拒绝规则、询问规则、权限模式、允许规则和 canUseTool callback 的处理顺序。某些交互工具、管理规则、受保护路径和自动模式下的动作存在特殊分支，因此不能把本教程的三行 if 当成真实系统的逐行源码。

允许 Hook 不代表绕过所有拒绝

在真实 SDK 中，PreToolUse 的 allow 不必然覆盖 deny 或 ask；管理策略和关键路径检查有独立作用。安全审核应按当前版本的完整规则顺序进行。

实现一个极小的 Fail-Closed 教学策略

源文件 permission_policy.py 只支持完整工具名和三种自定义教学模式，不解析 Claude Code 的参数通配符、自动分类器、工作区目录或 Hook。

policy = Policy(
    deny=frozenset({"Write"}),
    ask=frozenset({"Edit"}),
    allow=frozenset({"Read", "Edit"}),
    mode="manual",
)
assert policy.decide("Write", approved_by_user=True) == "deny"
assert policy.decide("Edit") == "ask"
assert policy.decide("Edit", approved_by_user=True) == "allow"

这能证明关键策略顺序：拒绝不因用户先前的概括性批准而被覆盖；询问不能因允许集合中出现同名工具而被跳过；无人值守模式遇到未获批准的工具默认拒绝。

不能仅依赖分类器、命令黑名单或 Prompt

规则与审批是纵深防御的一部分，不应被当作唯一隔离层。真实系统还需要工作目录限制、网络控制、操作系统级沙箱、凭证边界、敏感日志清理、可信配置来源与审计。在 Bash 中，命令字符串可能通过参数、重定向或复合命令产生非预期副作用，简单的字符串关键字拦截并不足够。

即使某种自动模式在文档中提供分类器，也不能将分类器判断结果视为可替代一切策略的数学证明。测试应覆盖最坏情况下的拒绝与越界操作，而不仅是正常批准流程。

测试拒绝优先和不能自动提权

运行 python3 -m unittest discover -s examples -p 'test_*.py'。测试覆盖：同时匹配 deny/ask/allow 时 deny 优先，ask 必须经过本次批准，read_only 模式拒绝 Write，无人值守不静默放行未知工具。

练习：给策略评估结果新增机器可读 reason 及审计 ID。写出“更具体 allow 不覆盖 deny”的测试，并说明如果要支持真实 Bash 规则，需要读取哪些平台文档，而不能直接套用自建的名称匹配。
