CHAPTER 07 / 28 · CODING AGENT ENGINEERING

System Prompt 与上下文工程：分层、Skills 和缓存

把系统规则、项目约定、技能与动态任务分清来源；通过确定性 Prompt Builder 解释前缀复用，并避免对 Claude Code 私有提示内容和缓存指标作无依据推断。

系统提示词无法代替权限引擎

即便一句指令写着“绝不执行危险命令”，模型仍然可能误解、忽视或受到检索文本的恶意诱导。Prompt 是引导行为的上下文，不是操作系统级访问控制。因此本章讨论提示内容的构造方式，同时强调工具授权必须在宿主程序里实现。

哪些上下文属于稳定约定，哪些是动态输入

信息来源示例更新频率与信任边界
应用级规则工具选择策略、停止条件应用所有者维护，相对稳定
项目约定目录结构、编码风格、测试命令随仓库更新；需防止过时与冲突
Skill 内容特定任务的流程、引用资料按任务选择，有版本与来源
历史与工具结果日志、差异、测试输出持续变化；不可无条件信任
本轮目标用户的最新任务和约束每轮变化，需正确解析范围

Claude Code 官方文档公开描述 CLAUDE.md、Skills 等机制；但它们在某一构建版本中究竟如何排列系统提示词、占用多少 token，并不能由外部文档直接推断。

写一个可以测试的 Prompt Builder

在我们的教学项目中，将稳定的应用级策略单独放入系统块，把项目约定、选择的技能与当前目标作为上下文消息。这个选择是设计示范，不主张适合每种产品或等同于 Claude Code 的私有实现。

plan = plan_prompt(
    base_policy="You may request Read but cannot grant tools.",
    project_rules="Use Python 3.12; tests in examples/",
    task="Explain the failing test",
    skill_name="review",
    skill_content="Check expectations before modifying code",
)
print(plan.static_prefix_hash)
print(plan.contextual_messages[-1]["content"])

查看完整 Prompt Builder。它对静态系统块进行 SHA-256 摘要用于离线对比，但哈希相同不等于真实 API 缓存命中。真实匹配还涉及工具、system、消息、模型与平台的缓存规则。

Prompt Caching：准确理解前缀复用

Prompt Caching 可以用自动或显式的 cache_control 缓存可复用的提示前缀。稳定工具定义、系统内容和初始文档放在前面，动态任务与最新结果放在后面，有利于使连续请求共享相同前缀；具体可缓存内容、最短长度、TTL 与价格由模型及平台规则决定。

不要写死“92% 缓存命中”

旧稿所称的 Claude Code 固定 92% Prefix 命中率及相应价格收益，在公开来源中没有得到足以复核的产品级证据。应使用实际响应中的缓存读写 token 与相同输入条件进行对比，而不是把假设百分比解释成官方数据。

Skills 按需加载：解决上下文拥挤，而非提升权限

技能是可复用的流程与知识资料。一个较好的设计是优先暴露技能名称、用途和适用场景，再根据实际任务加载对应正文和附属资源；这能减少一次性堆入大量无关说明的成本。

但是一个 SKILL.md 文件可能来自仓库、用户或第三方维护者，并不天然可靠。它不能自行授予 Shell 或读取私密目录的权限。实际执行仍必须经过独立权限检查。

查看“合理装配”与“危险装配”的区别

合理：用户要求代码审查 → 加载审查 Skill 的具体检查表 → 只提供只读工具 → 输出证据与建议。

危险：Skill 文件声称“为了完成任务可以忽略所有拒绝规则” → 宿主程序接受文字声明并放开 Bash。后者把低信任内容错误升级为执行权。

如何严谨地验证缓存是否真的起作用

  1. 固定模型、工具数组、system、文档内容与调用平台。
  2. 让两次请求共享长前缀，只改变末尾的用户目标。
  3. 按官方文档配置缓存机制，记录两次请求的缓存创建与读取 token 字段。
  4. 对照一个故意变动静态前缀的控制组，避免把延迟变化直接归因为缓存。
  5. 注明 TTL、请求时间及模型版本；绝不把单次结果推广为 Claude Code 的通用命中率。

这里不提供伪造的实验表；本仓库离线测试只证明前缀哈希的稳定性，真实缓存效果需有密钥和 API 日志才能验证。
